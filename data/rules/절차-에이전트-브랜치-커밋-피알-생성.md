# 에이전트 브랜치 커밋 및 PR 생성 가이드

## 목적
- 에이전트가 브랜치 전략에 맞춰 일관되게 작업하고 PR까지 생성할 수 있도록 표준 절차를 제공한다.
- 단일 주제 단일 pr 원칙을 준수한다.
- 나누어 작업한 경우, 작업마다 브랜치를 생성, 각 브랜치마다 PR을 생성한다.
- 리뷰의 편의와 작업의 용이, 관리, 추적을 위함

## 중요 원칙
- 단일 PR 단일 주제: 하나의 PR은 하나의 주제만 다룬다.
- 에이전트는 PR 생성 후 해당 원칙을 준수했는지 반드시 검증한다.
- 에이전트는 작성한 PR 제목/본문을 사용자에게 먼저 확인받고, 명시적 승인 후에만 PR을 생성한다.
- 이 저장소에서는 로컬 커밋을 사용자가 직접 수행하고, 에이전트는 수정, 스테이징 범위 점검, `pre-commit` 검증, 푸시, PR 생성을 담당하는 운영을 기본값으로 한다.
- 로컬 Git 훅은 저장소 추적 경로 `githooks/`와 `uv` 기반 실행을 기본값으로 한다.

## 브랜치 규칙
- 기준 브랜치: `main`, `dev`
- 기능 브랜치: `feat/agent-name/feature-name`
- 기타 브랜치: `etc/task-name` (단일 뎁스)
- 수정 브랜치: `fix/agent-name/issue-name`
- 원칙: 작업 시작 전에 반드시 새 브랜치를 먼저 생성한다.

## 사전 확인
1. 현재 브랜치 확인: `git branch --show-current`
2. 작업 트리 확인: `git status`
3. 최신 `dev` 반영:
   - `git checkout dev`
   - `git pull origin dev`

## 브랜치 생성
### 기능 작업
```bash
git checkout -b feat/<agent-name>/<feature-name>
```

### 버그 수정
```bash
git checkout -b fix/<agent-name>/<issue-name>
```

### 기타 작업
```bash
git checkout -b etc/<task-name>
```

## 변경사항 커밋
1. 변경 확인: `git status`, `git diff`
2. 커밋 전 실행 요건 확인:
   - 실행 스크립트를 `scripts/*.sh` 형태로 별도 작성했는지 확인한다.
   - 각 에이전트를 실행하는 스크립트가 준비되어 있는지 확인한다.
   - 새로 정의한 모듈에 직접 실행 진입점(예: `if __name__ == "__main__":`)이 있는지 확인한다.
3. 스크립트/모듈 실행 테스트를 수행한다.
4. 스테이징: `git add <path>` 또는 `git add .`
5. 스테이징한 파일 기준 `pre-commit` 검사를 수행한다.
   - 예시: `uv run pre-commit run --files <staged-files>`
   - `git commit --no-verify` 등 훅 우회 커밋은 허용하지 않는다.
6. 커밋:
```bash
git commit -m "feat: 변경 목적 중심으로 간결하게 작성"
```
7. 에이전트 실행 환경에서 로컬 커밋 권한/훅 문제가 반복되면, 사용자가 동일 스테이징 상태로 커밋하고 에이전트는 이후 푸시/PR 단계를 이어간다.

## 원격 푸시
```bash
git push -u origin HEAD
```

## PR 생성
### 원칙
- `feat/*`, `fix/*`, `etc/*` 브랜치는 `dev`로 PR을 생성한다.
- PR 제목은 변경 이유가 드러나게 작성한다.
- PR 본문에는 변경 요약과 테스트 결과를 포함한다.
- PR 본문은 마크다운 문법을 준수하여 작성한다.
- PR은 단일 주제만 포함하도록 작성한다.
- PR에는 milestone을 반드시 설정한다.
- PR label은 연결 이슈의 label과 일치하도록 맞춘다.
- PR 크기는 기본적으로 총 변경 줄 수 350줄 이하, 변경 파일 수 20개 이하를 유지한다.
- PR 생성 전, 에이전트는 초안(PR 제목/본문)을 사용자에게 공유하고 승인 여부를 확인한다.
- 사용자 승인 이전에는 `gh pr create`를 실행하지 않는다.
- CI에서 `pre-commit`이 강제로 실행되므로, PR 전에 동일 검사를 먼저 통과시킨다.

### CI 가이드
- `pr-policy-check`
  - PR 본문에 `Refs #<번호>` 또는 `Closes #<번호>`가 있는지 검사
  - PR milestone 설정 여부 검사
  - PR label 존재 여부 검사
  - 연결 이슈 label과 PR label 일치 여부 검사
  - PR 크기 제한 검사: 추가+삭제 합산 350줄 이하, 변경 파일 20개 이하
- `test`
  - 변경 파일 기준 `pre-commit` 검사 수행
  - `python -m compileall app/`로 `app/` 하위 Python 문법 검사

### PR 본문 템플릿
- 헤딩/불릿/테스트 섹션 구조를 사용한다.
- 최상단에 이슈 링크를 `Refs #18` 또는 별도 `## 연관 이슈` 섹션으로 명시
- 본문을 최소 2개 섹션으로 고정
   - `## 변경 내용`
   - `## 테스트`
- `## 변경 내용`은 번호 목록보다 불릿 중심으로 정리
- `## 테스트`는 체크박스 목록으로 정리
- 필요 시 `## 영향 범위` 섹션을 추가해 리뷰어가 리스크를 빠르게 파악하도록 구성
- 예시 템플릿:
```
## 연관 이슈
- Refs #18

## 변경 내용
- 상태 모델을 Pydantic BaseModel로 표준화
- 오케스트레이터 fan-out 병렬 실행 및 상태 머지 로직 적용
- products_agent 데이터 경로를 data/doc, data/outputs로 정리
- pre-commit(ruff, ruff-format) 도입

## 테스트
- [ ] 로컬 테스트 완료
- [ ] 회귀 영향 확인
- [ ] pre-commit 통과

```
### GitHub CLI 예시
```bash
gh pr create --base dev --head HEAD \
  --title "feat: 기능 요약" \
  --body "## 변경 내용
- 핵심 변경 1
- 핵심 변경 2

## 테스트
- [ ] 로컬 테스트 완료
- [ ] 회귀 영향 확인"
```

## 작업 완료 체크리스트
- [ ] 브랜치가 네이밍 규칙(`feat/*`, `fix/*`, `etc/*`)을 준수함
- [ ] `dev` 최신 상태 기반으로 작업함
- [ ] 실행 스크립트를 `scripts/*.sh`로 별도 작성함
- [ ] 에이전트별 실행 스크립트를 사전 준비함
- [ ] 신규 모듈에 `if __name__ == "__main__":` 진입점을 작성함
- [ ] 스크립트/모듈 실행 테스트를 완료함
- [ ] 커밋 전 스테이징한 파일 기준 `pre-commit` 검증을 통과함
- [ ] 로컬 Git 훅이 `githooks/` + `uv` 기준으로 동작하는지 확인함
- [ ] 변경 파일만 스테이징 및 커밋함
- [ ] 원격 브랜치 푸시 완료
- [ ] PR milestone 설정 완료
- [ ] PR label이 연결 이슈 label과 일치함
- [ ] PR 크기 제한(총 350줄 이하, 파일 20개 이하)을 확인함
- [ ] PR 제목/본문 초안을 사용자에게 공유하고 승인받음
- [ ] `dev` 대상 PR 생성 완료
- [ ] 생성한 PR이 단일 PR 단일 주제 원칙을 준수하는지 검증함
