## 대표 프로젝트

### company_analyzer
- 분산된 JD, 기술 블로그, 제품 문서, GitHub 저장소를 하나의 분석 흐름으로 묶으면서도 결과의 출처를 추적할 수 있도록 LangGraph 기반 멀티에이전트 파이프라인을 설계했습니다. 수집과 해석이 뒤섞이면 분석 신뢰성을 설명하기 어렵기 때문에 `service_agent` 중심의 단계별 구조로 분리했습니다.
- 기업 요구 역량과 사용자 보유 역량을 분리 분석한 뒤 연결하는 흐름을 설계했습니다. 지원 과정에서는 경험 총량보다 `왜 적합한지`를 설명하는 근거가 중요하다고 봤기 때문에, 적합성 설명까지 이어지는 포트폴리오 생성 구조로 확장했습니다.

### job-analyzer
- 저장소 코드를 단순 기술 키워드가 아니라 구조와 역할까지 해석하기 위해 Python AST 정적 분석과 임베딩 기반 유사도 계산을 결합한 분석 구조를 구현했습니다.
- JD 분석, 저장소 분석, 외부 정보 수집을 묶어 기술 경험을 업무 가치 언어로 바꾸는 흐름을 만들었습니다. 기술 역량을 비즈니스 가치와 연결해 설명하기 어려운 문제를 줄이기 위한 접근이었습니다.

### trade-onboarding-agent
- 멀티모드 에이전트에서 stale state와 비동기 처리 누락 문제를 수정했습니다. 교육형 챗봇은 답변 내용보다 먼저 상태 일관성과 처리 안정성이 확보되어야 반복 사용이 가능하다고 판단했습니다.
- 리스크 분석, 이메일 초안, 퀴즈 생성 기능을 업무 단위로 분리했습니다. 실제 교육 현장에서는 일반 질의응답보다 상황 판단, 문서 작성, 이해 점검이 이어지는 구조가 더 중요하기 때문입니다.

### idol_agent_LUMI
- LiteLLM fallback, checkpoint, 비용 추적, Langfuse 연동을 포함한 운영형 구조를 구현했습니다. 생성 기능만 있는 데모로는 실제 운영이 어렵기 때문에 장애 대응과 추적 가능성을 우선 설계했습니다.
- 세션 유실, 장애, 비용 폭증이 서비스 신뢰를 무너뜨리는 핵심 요인이라고 보고, 사용자가 지속적으로 사용할 수 있는 AI 경험을 목표로 제품 구조를 정리했습니다.

### manufacturing-ai-coach
- 센서 데이터, 유지보수 이력, SOP 문서를 함께 참조하는 RAG 기반 복합 데이터 진단 구조를 설계했습니다. 제조 현장 문제는 단일 데이터만으로 해석하면 오판 가능성이 높다고 판단했기 때문입니다.
- 진단, 문서 검색, 추천 조치, 확인 흐름을 연결해 유지보수 의사결정 보조 도구로 설명 가능한 구조를 만들었습니다. 현장에서는 정보 조회보다 다음 행동 판단이 더 큰 가치이기 때문입니다.
