# 마스터 리줌 저장소 원노트

목적: 리줌과 포트폴리오 문장으로 압축하기 전에 저장소 기준의 검증 가능한 원재료를 남긴다.

## 작성 원칙
- 확인된 코드, 문서, 커밋만 근거로 쓴다.
- 추정이 필요한 부분은 `추정`으로 명시한다.
- 모든 프로젝트는 아래 두 관점으로 모두 정리한다.
  - `기술문제 해결 관점`
  - `비즈니스문제 해결 관점`
- 두 관점 모두 `무엇을 했다`에서 멈추지 않고 `왜 그렇게 풀었는지`, `왜 중요한지`까지 적는다.

## 정리 형식

### 기술문제 해결 관점
- 무엇이 기술문제였는가
- 왜 그 문제를 그런 방식으로 풀어야 했는가
- 어떤 구조와 기술로 구현했는가
- 결과적으로 무엇이 좋아졌는가

### 비즈니스문제 해결 관점
- 무엇이 사용자·조직·업무 문제였는가
- 왜 그 문제가 중요한가
- 어떤 방식으로 기여했는가
- 결과적으로 어떤 가치가 생겼는가

- 요구 역량과 보유 역량을 매핑해 최종 포트폴리오 생성까지 연결

### 기술문제 해결 관점

- 결과: 분석 흐름의 책임 경계가 분명해져 추적, 수정, 후속 확장이 쉬운 구조를 확보했습니다.

### 비즈니스문제 해결 관점

- 왜 중요한가: 지원 과정에서는 경험 총량보다 기업 요구와 자신의 경험을 연결해 설명하는 능력이 실제 의사결정에 더 큰 영향을 주기 때문입니다.
- 기여 방식: 기업 측 요구와 사용자 측 경험을 분리해 분석한 뒤, 둘을 연결하는 결과물 생성 흐름을 설계했습니다.
- 결과: 단순 요약이 아닌 `적합성 설명 도구`로 확장 가능한 구조를 만들었습니다.

### 기술문제 해결 관점
- 기술문제: 멀티모드 에이전트에서 비동기 처리 누락과 stale state 문제로 응답 흐름이 불안정했습니다.
- 왜 그렇게 풀었는가: 교육용 챗봇은 답변 내용보다 먼저 상태 일관성과 요청 처리 안정성이 확보되어야 반복 사용이 가능하기 때문입니다.
- 구현 방식: `orchestrator`와 `riskmanaging` 중심으로 비동기 처리, 상태 전이, 누락된 `await`를 보강했습니다.
- 결과: 멀티턴 상호작용과 모드 전환을 감당할 수 있는 안정적 백엔드 흐름을 확보했습니다.

### 비즈니스문제 해결 관점
- 비즈니스 문제: 무역 실무 학습은 단순 설명보다 리스크 판단, 문서 작성, 이해 점검이 함께 필요합니다.
- 왜 중요한가: 실제 업무 교육은 일반 질의응답보다 업무 흐름을 따라갈 수 있을 때 체감 가치가 커지기 때문입니다.
- 기여 방식: 리스크 분석, 이메일 초안, 퀴즈 생성 등 업무 단위 기능을 분리해 사용할 수 있도록 구성했습니다.
- 결과: 단순 챗봇이 아닌 `교육 + 업무 보조` 성격의 도구로 설명 가능한 구조를 갖췄습니다.

- LangGraph
- LangChain
- ChromaDB
- React
- Redis
- Celery

### 기술문제 해결 관점
- 기술문제: 실시간 데이터, 과거 기록, 문서 지식을 하나의 진단 흐름으로 연결해야 했습니다.
- 왜 그렇게 풀었는가: 제조 현장 문제는 단일 센서값이나 단일 문서만으로 해석하면 오판 가능성이 높아, 상태 데이터와 지식 문서를 함께 참조하는 구조가 필요했습니다.

- 결과: 진단과 추천 조치를 하나의 파이프라인으로 설명할 수 있는 구조를 만들었습니다.

### 비즈니스문제 해결 관점
- 비즈니스 문제: 현장에서는 정보 조회 자체보다 다음 조치를 빠르게 판단하는 것이 중요합니다.

- 기여 방식: 진단, 문서 검색, 추천 조치, 확인 흐름을 연결해 작업자가 후속 행동을 정할 수 있게 했습니다.
- 결과: 단순 조회 도구가 아닌 유지보수 의사결정 보조 도구로 설명 가능합니다.
