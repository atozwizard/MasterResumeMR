# A트랙 대표 bullet 확정 1차 2026-03-13

## 목적
최우선 5개 프로젝트에 대해 마스터 리줌과 직무별 리줌에 공통으로 사용할 대표 bullet을 확정한다.

## 사용 원칙
- 각 프로젝트마다 `기술문제 해결형 1개`, `비즈니스문제 해결형 1개`를 기본으로 둔다.
- 각 bullet은 `문제 -> 왜 -> 행동 -> 기술 -> 결과` 흐름을 유지한다.
- 수치가 없으면 과장하지 않고 구조적 결과와 사용자 가치 중심으로 쓴다.

## 1. `company_analyzer`

### 기술문제 해결형
- 분산된 JD, 기술 블로그, 제품 문서, GitHub 저장소를 하나의 분석 흐름으로 묶으면서도 결과의 출처를 추적할 수 있도록 LangGraph 기반 멀티에이전트 파이프라인을 설계했습니다. 수집 단계와 해석 단계가 뒤섞이면 분석 신뢰성을 설명하기 어렵다고 판단해 `service_agent` 중심의 단계별 노드 구조로 분리했고, 그 결과 추적성과 후속 확장성이 높은 분석 구조를 확보했습니다.

### 비즈니스문제 해결형
- 기업 요구 역량과 사용자 보유 역량을 분리 분석한 뒤 연결하는 흐름을 설계했습니다. 지원 문서에서는 경험 총량보다 `왜 이 포지션에 적합한지`를 설명하는 근거가 중요하다고 봤기 때문에, 단순 요약이 아니라 적합성 설명까지 이어지는 포트폴리오 생성 구조로 확장했습니다.

### 근거
- 파일: `app/agents/service_agent/graph.py`, `app/agents/service_agent/nodes/*`
- 커밋: `2f3d840`, `0ce498c`, `5c353aa`

## 2. `job-analyzer`

### 기술문제 해결형
- 저장소 코드를 단순 키워드 수준이 아니라 구조와 역할까지 해석하기 위해 Python AST 정적 분석과 임베딩 기반 유사도 계산을 결합한 분석 구조를 구현했습니다. 기술 나열만으로는 직무 적합성과 비즈니스 가치 연결이 약해진다고 판단했기 때문에, 코드가 왜 중요한지 설명 가능한 분석 기반을 만드는 데 집중했습니다.

### 비즈니스문제 해결형
- JD 분석, 저장소 분석, 외부 정보 수집을 묶어 기술 경험을 업무 가치 언어로 바꾸는 흐름을 만들었습니다. 지원자와 기업 모두 기술 경험이 실제 업무에 어떤 가치를 주는지 빠르게 해석하기 어렵다는 문제를 줄이기 위해, 직무 적합성을 설명하는 근거 생성 도구로 확장했습니다.

### 근거
- 파일: `agent_core.py`, `analysis_utils.py`, `agent_graph.py`, `jd_matching.py`
- 커밋: `f062041`, `3ba52e2`, `649decd`

## 3. `trade-onboarding-agent`

### 기술문제 해결형
- 멀티모드 에이전트에서 stale state와 비동기 처리 누락으로 발생하던 응답 불안정 문제를 수정했습니다. 교육용 챗봇은 답변 품질 이전에 상태 일관성과 요청 처리 안정성이 보장되어야 반복 사용이 가능하다고 판단해, `orchestrator`와 `riskmanaging` 중심으로 비동기 흐름과 상태 전이를 보강했습니다.

### 비즈니스문제 해결형
- 무역 실무 학습이 단순 질의응답에 머물지 않도록 리스크 분석, 이메일 초안, 퀴즈 생성 기능을 업무 단위로 분리했습니다. 실제 교육 현장에서는 설명보다 상황 판단, 문서 작성, 이해 점검까지 이어지는 흐름 지원이 더 중요하기 때문에, 챗봇을 `교육 + 업무 보조` 도구로 재구성했습니다.

### 근거
- 파일: `backend/agents/orchestrator.py`, `backend/agents/riskmanaging/*`, `backend/api/routes.py`
- 커밋: `4840e41`, `9025933`, `4f05d8f`

## 4. `idol_agent_LUMI`

### 기술문제 해결형
- 서비스형 AI에서 모델 호출 실패, 세션 지속성, 비용 추적, 관측성 부재 문제를 줄이기 위해 LiteLLM fallback, checkpoint, 비용 추적, Langfuse 연동을 포함한 운영형 구조를 구현했습니다. 생성 기능만 있는 데모로는 실제 운영이 어렵다고 판단했기 때문에, 장애 대응과 추적 가능성을 우선 설계했습니다.

### 비즈니스문제 해결형
- 사용자가 일회성 데모가 아니라 지속 사용 가능한 AI 경험을 얻도록 운영 가시성과 복구 가능성을 제품 구조 안에 넣었습니다. 세션 유실, 장애, 비용 폭증은 기능 품질과 무관하게 서비스 신뢰를 무너뜨리기 때문에, 운영 가능한 제품 후보로 설명할 수 있는 방향으로 구조를 정리했습니다.

### 근거
- 파일: `app/core/llm.py`, `app/core/checkpointer.py`, `app/core/cost_tracker.py`, `app/core/tracing.py`
- 커밋: `ec2bbc8`, `0662dde`, `7c027d3`

## 5. `manufacturing-ai-coach`

### 기술문제 해결형
- 센서 데이터, 유지보수 이력, SOP 문서를 하나의 진단 흐름으로 연결하기 위해 RAG 기반 복합 데이터 진단 구조를 설계했습니다. 제조 현장 문제는 단일 데이터만으로 해석하면 오판 가능성이 높다고 보고, 상태 데이터와 문서 지식을 함께 참조하는 파이프라인으로 구성했습니다.

### 비즈니스문제 해결형
- 현장에서 단순 정보 조회보다 다음 조치를 빠르게 판단하는 것이 더 중요하다고 보고, 진단, 문서 검색, 추천 조치, 확인 흐름을 연결했습니다. 판단 지연 자체가 비용과 다운타임으로 이어질 수 있기 때문에, 유지보수 의사결정 보조 도구로 설명 가능한 구조를 만들었습니다.

### 근거
- 파일: `backend/agents/manufacturing_agent.py`, `backend/api/diagnosis.py`, `backend/services/rag_service.py`
- 커밋: `e74b7ef`
