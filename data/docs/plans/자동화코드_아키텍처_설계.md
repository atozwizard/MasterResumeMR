# 자동화 코드 아키텍처 설계

## 목적
마스터 리줌 자동화 시스템을 그래프 기반 파이프라인으로 설계한다. 핵심은 각 프로젝트를 `기술문제 해결`과 `비즈니스문제 해결` 두 관점으로 해석하고, 두 관점 모두 `왜`를 포함한 근거 문장으로 연결하는 것이다.

## 설계 원칙
- 그래프 상태에는 결과뿐 아니라 `왜`를 남기는 필드를 둔다.
- 노드는 `자료 수집`, `근거 추출`, `이유 추출`, `bullet 생성`, `품질 점검` 역할로 나눈다.
- 엣지는 실패 복구와 재시도를 고려해 단순하고 명확하게 유지한다.
- 툴은 문서, 저장소, 커밋, 환경설정 파일을 각각 읽고 해석하는 역할로 분리한다.

## 그래프 상태
```python
class ResumeGraphState(TypedDict, total=False):
    target_roles: list[str]
    documents: list[dict]
    repositories: list[dict]
    readme_audit: list[dict]
    project_profiles: list[dict]
    contribution_evidence: list[dict]
    technical_why_notes: list[dict]
    business_why_notes: list[dict]
    raw_notes: list[dict]
    bullets: dict[str, list[str]]
    quality_issues: list[str]
```

## 노드 설계

### 1. 자료 수집 노드
- `collect_documents`
  - `data/` 문서를 수집하고 형식을 분류한다.
- `collect_repositories`
  - `repo/` 저장소를 수집하고 기본 메타데이터를 만든다.

### 2. 저장소 해석 노드
- `audit_readme`
  - README 품질을 `충분`, `보완 필요`, `부재`로 분류한다.
- `analyze_structure`
  - 디렉터리 구조, 엔트리포인트, 설정 파일, API/에이전트/프론트엔드 여부를 해석한다.
- `analyze_commits`
  - 작성자 기준 기여가 강한 파일과 커밋을 추출한다.

### 3. 이유 추출 노드
- `extract_technical_why`
  - 프로젝트가 어떤 기술문제를 풀었는지 추출한다.
  - 왜 해당 구조와 기술을 선택했는지 정리한다.
- `extract_business_why`
  - 프로젝트가 어떤 사용자·조직·업무 문제를 풀었는지 추출한다.
  - 왜 그 문제가 중요한지 정리한다.

### 4. 문장 생성 노드
- `build_raw_notes`
  - 프로젝트별 원노트를 두 관점으로 정리한다.
- `build_bullets`
  - 직무별 bullet을 생성한다.
  - 각 bullet은 `문제 -> 왜 -> 행동 -> 기술 -> 결과` 흐름을 유지한다.

### 5. 품질 점검 노드
- `quality_check`
  - 수치 없는 과장 표현 감지
  - `왜`가 빠진 bullet 감지
  - 기술 관점만 있고 비즈니스 관점이 없는 bullet 감지
  - 근거 없는 성과 표현 감지

## 툴 설계

### `file_reader`
- Markdown, TXT, PDF를 읽는다.

### `repo_reader`
- README, `pyproject.toml`, `requirements.txt`, `package.json`, `.env.example`를 읽는다.

### `commit_reader`
- 커밋 로그, 작성자, 파일 변경 패턴을 읽는다.

### `env_reader`
- `.env`, `.env.example`에서 사용 가능한 API와 외부 서비스 단서를 읽는다.

### `document_parser`
- 자기소개서, 메모, PDF에서 프로젝트명, 기술, 역할, 성과 후보를 추출한다.

## 엣지 설계
```text
collect_documents -> collect_repositories
collect_repositories -> audit_readme
audit_readme -> analyze_structure
analyze_structure -> analyze_commits
analyze_commits -> extract_technical_why
extract_technical_why -> extract_business_why
extract_business_why -> build_raw_notes
build_raw_notes -> build_bullets
build_bullets -> quality_check
quality_check -> END
```

## 그래프 설계 포인트
- `기술문제 해결`과 `비즈니스문제 해결`은 별도 노드로 분리한다.
- 두 관점의 `왜`를 분리 저장해야, 나중에 직무별 리줌에서 강조점을 바꿔도 근거가 남는다.
- `quality_check`에서 `왜`가 없는 bullet을 자동으로 걸러야 한다.

## 환경설정 기반 사용 가능 API 후보
`.env` 또는 `.env.example`에서 확인 가능한 항목은 아래 범주로 해석한다.
- LLM API
  - Upstage
  - Llama API
  - LiteLLM
- 검색 및 수집
  - Serper
- 관측성과 평가
  - LangSmith
- 저장소와 세션
  - Supabase
  - Redis
- 선택형 확장
  - MQTT
  - Kafka

## 품질 기준
- 프로젝트마다 두 관점이 모두 존재해야 한다.
- 두 관점 모두 `왜` 문장이 있어야 한다.
- 최종 bullet은 직무 적합성과 근거 파일까지 연결 가능해야 한다.
