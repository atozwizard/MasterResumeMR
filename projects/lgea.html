02. LGEA

persona 기반 모델 가드레일 붕괴 테스트

실행 중인 LUMI FastAPI와 내부 service surface를 실제로 두드려, 질문 실행 → 채점 → 비교 분석 → 보고서 생성까지 분리한 모델 평가 워크스페이스입니다.

핵심 메시지

LGEA는 챗봇 기능을 하나 더 붙인 프로젝트가 아니라, persona에 따라 모델의 가드레일이 어느 표면에서 무너지는지 반복 가능하게 확인하는 평가 체계입니다.

왜 따로 필요했는가

LUMI를 서비스로 운영하는 것과, 그 서비스가 어떤 질문에서 어떤 표면에서 약해지는지 평가하는 것은 다른 일입니다. 서비스 코드 안에 평가 로직을 섞으면 재현성이 깨지고, 응답을 한 번 확인한 뒤 끝나는 테스트로 남기 쉽습니다.

flowchart LR A[서비스 운영 코드만 존재] --> B[평가 로직이 산발적으로 섞임] B --> C[같은 조건 재실행 어려움] C --> D[표면별 응답 차이 추적 어려움] D --> E[가드레일 평가 근거 약화]

무엇을 테스트했는가

  • 실제 LUMI FastAPI /api/v1/chat/
  • 내부 service surface: router, response-layer, rag, tool
  • baseline_questions.json 기반 공통 질문 세트
  • abuse category, benign probe, persona source와 모델 조합
flowchart LR A[질문 세트] --> B[FastAPI 응답] A --> C[router] A --> D[response-layer] A --> E[rag] A --> F[tool] B --> G[채점] C --> G D --> G E --> G F --> G

어떻게 구현했는가

  1. baseline_questions.json의 질문을 준비합니다.
  2. 같은 질문 세트를 FastAPI와 service surface에 보냅니다.
  3. 실행 결과를 results.jsonl, fastapi_live_results.jsonl, service_surface_results.jsonl로 남깁니다.
  4. judge 단계에서 최종 응답만 추려 채점합니다.
  5. analysis 단계에서 표면, 카테고리, 모델 단위로 통계를 만듭니다.
  6. report 단계에서 한국어 보고서와 thesis-ready 문서를 생성합니다.
flowchart LR A[baseline questions] --> B[runner] B --> C[FastAPI live run] B --> D[service surface run] C --> E[results.jsonl] D --> E E --> F[judge] F --> G[scored_results.jsonl] G --> H[analysis] H --> I[summary.json / comparative stats] I --> J[report generation]

무엇을 남겼는가

  • 실행 결과: LGEA/data/runs/*.jsonl
  • 채점 결과: LGEA/data/judge/*.jsonl
  • 분석 요약: LGEA/data/analysis/*.json
  • 연구 자산: experiment_matrix.json, repetition_plan.json, persona_summary.json
  • 보고서: thesis_ready_report_ko.md, cross_surface_analysis_ko.md, comparative_stats_ko.md

결과와 의미

LUMI 서비스와 평가 레이어를 분리해 설명할 수 있는 구조가 생겼고, 단순 테스트가 아니라 질문 세트, 실행 결과, 채점, 통계, 보고서가 남는 평가 체계를 만들었습니다. 이 프로젝트는 단순 응답 테스트가 아니라 persona에 따른 모델 가드레일 붕괴를 표면별로 비교하고 근거 파일과 보고서로 남기는 평가 체계라는 점이 중요합니다.
