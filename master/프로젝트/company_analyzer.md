# 프로젝트_문제해결_서비스보고서

## 프로젝트명
`company_analyzer`

## 한 줄 요약
기업이 실제로 원하는 역량과 사용자가 보유한 경험을 같은 언어로 비교할 수 있도록, 분산된 근거를 수집·분석·매핑하는 멀티에이전트 분석 프로젝트.

## 1. problem solve 관점

### 어떤 문제를 다루는가
- 채용 공고, 기술 블로그, 제품 문서, GitHub 저장소가 서로 다른 형식으로 흩어져 있어 기업 요구 역량을 한 번에 읽기 어렵다.
- 사용자 경험도 저장소, 커밋, 프로젝트 문서, 서술형 경력으로 분산되어 있어 보유 역량을 설명 가능한 형태로 구조화하기 어렵다.
- 단순 키워드 비교만으로는 `이 기술이 실제로 어떤 업무 가치와 연결되는지`를 설득력 있게 보여주기 어렵다.

### 왜 이 문제를 이런 방식으로 풀어야 했는가
- 채용 적합도는 단순 매칭이 아니라 `기업 요구 역량의 구조화`와 `사용자 경험의 구조화`가 동시에 되어야 설명 가능해진다.
- 한 번에 하나의 문서만 읽는 방식으로는 출처 추적성이 떨어지고, 분석 결과의 신뢰도를 방어하기 어렵다.
- 따라서 수집, 분석, 근거 통합, 요구 역량 매핑을 역할별 에이전트로 분리한 뒤 오케스트레이션하는 구조가 필요하다.

### 어떻게 구현했는가
- `company_orchestrator_agent`와 `user_orchestrator_agent`를 중심으로 기업 분석 흐름과 사용자 분석 흐름을 병렬 구조로 분리했다.
- `repository_agent`, `service_agent`, `job_description_agent`, `tech_blog_agent`로 기업 측 근거를 수집했다.
- `raw_agent`, `outline_agent`, `commit_agent`, `episode_agent`로 사용자 경험을 raw 데이터, 개요, 커밋, 스토리 단위로 분해했다.
- `collector_agent`, `requirement_agent`를 통해 근거를 통합하고 요구 역량과 경험 단위를 연결하는 매핑 단계를 구성했다.

### 무엇이 핵심 결과인가
- 기업 요구 역량과 사용자 보유 역량을 서로 다른 문서 묶음이 아니라 `비교 가능한 분석 단위`로 바꾸는 구조를 만들었다.
- 결과물에 어떤 출처가 사용되었는지 추적 가능한 파이프라인으로 정리해, 리포트 신뢰도를 방어할 수 있는 기반을 마련했다.
- 프로젝트 자체가 `포트폴리오 생성 에이전트`이자 `설명 가능한 적합도 분석 시스템`으로 해석될 수 있게 되었다.

## 2. project service 관점

### 이 프로젝트는 어떤 서비스인가
- 구직자나 지원자의 경험을 기업 요구 사항과 연결해 해석해 주는 `적합도 분석 서비스`에 가깝다.
- 동시에 기업을 분석하는 관점과 사용자를 분석하는 관점을 분리해, 두 데이터를 하나의 리포트로 엮어내는 `설명형 분석 도구`이기도 하다.

### 사용자에게 주는 가치
- 사용자는 자신의 경험을 `내가 무엇을 했다` 수준이 아니라 `기업이 요구하는 역량과 어떻게 연결되는가`로 다시 볼 수 있다.
- 기업 분석 결과와 사용자 분석 결과가 같은 프레임으로 정리되기 때문에, 지원 문서 작성과 포트폴리오 설계에 직접 활용할 수 있다.
- 분석 결과에 근거 출처가 남기 때문에, 면접이나 자기소개서 단계에서 방어 가능한 재료를 확보할 수 있다.

### 서비스 구조상 중요한 포인트
- 기업 측 분석과 사용자 측 분석을 병렬로 나눈 뒤 마지막에 매핑하는 구조라서 확장성이 높다.
- 특정 입력 소스가 부실해도 다른 에이전트 근거를 함께 묶어 보완할 수 있다.
- 최종 목표가 단순 요약이 아니라 `포트폴리오 생성`이므로, 분석 결과가 문서형 산출물로 이어지도록 설계되어 있다.

## 3. 리줌에서 말할 수 있는 포인트
- 분산된 채용/제품/기술/저장소 정보를 수집해 설명 가능한 적합도 분석 구조를 설계
- 기업 요구 역량과 사용자 보유 역량을 병렬 분석 후 매핑하는 멀티에이전트 파이프라인 구성
- 포트폴리오 생성까지 고려한 분석형 AI 서비스 구조 설계 경험
